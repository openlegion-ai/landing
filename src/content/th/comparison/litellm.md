# ทางเลือกสำหรับ LiteLLM: OpenLegion Distributed Vault เทียบกับ Centralized Gateway

OpenLegion เทียบกับ LiteLLM แสดงถึงการแลกเปลี่ยนด้านความปลอดภัยพื้นฐานระหว่างข้อมูลรับรองที่เก็บใน vault และถูกฉีดเข้าไปนอกโมเดล กับการรวมข้อมูลรับรองผ่าน LLM gateway แบบรวมศูนย์ LiteLLM โดดเด่นในฐานะ unified provider gateway ด้วย 62,615 GitHub stars การติดตามต้นทุน และการรองรับ LLM provider กว่า 100 ราย แต่ได้รับผลกระทบจาก CVE-2026-42208 (CVSS 9.8 CRITICAL, อยู่ในแคตตาล็อก Known Exploited Vulnerabilities ของ CISA) ซึ่ง SQL injection เปิดเผยฐานข้อมูลข้อมูลรับรองทั้งหมดให้กับผู้โจมตีที่ไม่ผ่านการรับรองความถูกต้อง ใน OpenLegion ข้อมูลรับรองอยู่ใน vault และถูกฉีดในเวลาที่เรียกใช้ โดยโมเดลถือเพียง handle เท่านั้น — ไม่มีฐานข้อมูลข้อมูลรับรองให้อ่าน ซึ่งกำจัดเป้าหมายการโจมตีมูลค่าสูงที่ gateway แบบรวมศูนย์สร้างขึ้นตามโครงสร้าง

> **LiteLLM คืออะไร และเปรียบเทียบกับ OpenLegion อย่างไร?**
> LiteLLM คือ LLM gateway แบบรวมศูนย์ที่มีมากกว่า 62,615 GitHub stars ซึ่งรวมข้อมูลรับรองของผู้ให้บริการในฐานข้อมูลเดียวสำหรับการเข้าถึงแบบรวม การติดตามต้นทุน และการกำหนดเส้นทางผู้ให้บริการ OpenLegion คือแพลตฟอร์ม multi-agent ที่ให้ความสำคัญกับความปลอดภัย ซึ่งข้อมูลรับรองอยู่ใน vault และถูกฉีดเข้าไปนอกโมเดล ขจัดฐานข้อมูลข้อมูลรับรองในฐานะเป้าหมายการโจมตี

## Gateway แบบรวมศูนย์เทียบกับ Vault แบบกระจาย

CVE-2026-42208 แสดงให้เห็นความเสี่ยงนี้เมื่อ SQL injection เปิดเผยฐานข้อมูลข้อมูลรับรองทั้งหมดของ LiteLLM ให้กับผู้โจมตีที่ไม่ผ่านการรับรองความถูกต้อง

**OpenLegion** เก็บการเข้าถึงข้อมูลรับรองไว้ใน vault ที่ไม่เคยถูกคัดลอกไปยังตำแหน่งใดที่ agent เข้าถึงได้ เมื่อ agent เรียกใช้ ข้อมูลรับรองถูกฉีดเข้าไปนอกโมเดล ซึ่งถือเพียง handle เท่านั้น

## กลุ่ม CVE ปี 2026: เมื่อการรวมศูนย์กลายเป็นภาระ

### CVE-2026-42208: SQL Injection แบบ CRITICAL

ช่องโหว่ความรุนแรง **CVSS 9.8 CRITICAL** (คะแนน CVSS 3.1 ของ NVD ส่วนคะแนน CVSS 4.0 ของ GitHub คือ 9.3) ซึ่ง SQL injection ใน API key verification ของ LiteLLM เปิดเผยฐานข้อมูลข้อมูลรับรองทั้งหมดให้กับผู้โจมตีที่ไม่ผ่านการรับรองความถูกต้อง ช่องโหว่นี้กระทบเวอร์ชัน 1.81.16 ถึง 1.83.6 และได้รับการแพตช์ใน v1.83.7 CISA เพิ่มช่องโหว่นี้เข้าแคตตาล็อก Known Exploited Vulnerabilities เมื่อวันที่ 8 พฤษภาคม 2026 ซึ่งยืนยันว่ามีการโจมตีจริง

### รูปแบบ CVE ปี 2026: ห้าช่องโหว่ในสี่เดือน

**CVE ร้ายแรงห้ารายการ** ถูกเผยแพร่ระหว่างเดือนเมษายนถึงพฤษภาคม 2026 และเป็นเพียงส่วนหนึ่งของทั้งปี: NVD ระบุ CVE ของ LiteLLM ที่เผยแพร่ในปี 2026 มากกว่า 30 รายการ:

1. **CVE-2026-42208** (CVSS 9.8 CRITICAL) - SQL injection ที่เปิดเผยฐานข้อมูลข้อมูลรับรองให้กับผู้โจมตีที่ไม่ผ่านการรับรองความถูกต้อง แก้ไขใน v1.83.7
2. **CVE-2026-35029** (CVSS 8.8 HIGH) - ไม่มีการตรวจสิทธิ์ผู้ดูแลระบบบน `/config/update`: ผู้ใช้ที่ผ่านการรับรองความถูกต้องคนใดก็ได้สามารถเปลี่ยนการกำหนดค่า proxy และลงทะเบียน pass-through handler ที่ชี้ไปยังโค้ด Python ที่ผู้โจมตีควบคุม จนเกิด RCE แก้ไขใน v1.83.0
3. **CVE-2026-35030** (CVSS 9.1 CRITICAL) - คีย์แคชของ OIDC userinfo ชนกัน: เมื่อเปิดใช้การรับรองความถูกต้องแบบ JWT (ไม่ได้เปิดเป็นค่าเริ่มต้น) token ที่สร้างขึ้นให้ 20 อักขระแรกตรงกับ token ในแคชของผู้ใช้ที่ถูกต้องจะได้รับตัวตนของผู้ใช้นั้น แก้ไขใน v1.83.0
4. **CVE-2026-40217** (CVSS 8.8 HIGH) - การรันโค้ดผ่านการเขียน bytecode ใหม่ที่ `/guardrails/test_custom_code` ซึ่งเป็นการหนีออกจาก sandbox ใน custom-code guardrail แก้ไขใน v1.83.10
5. **CVE-2026-42203** (CVSS 8.8 HIGH) - Server-Side Template Injection (SSTI) RCE ที่ `/prompts/test`: prompt template ถูกเรนเดอร์โดยไม่มี sandbox ผู้ที่ถือ API key ของ proxy ที่ใช้งานได้จึงรันโค้ดในโปรเซสของ proxy ได้ กระทบเวอร์ชัน 1.80.5 ถึง 1.83.6 แก้ไขใน v1.83.7

## ความปลอดภัยของคอนเทนเนอร์: การดำเนินการ Root เทียบกับที่แยก

### การดำเนินการ Root ตามค่าเริ่มต้นของ LiteLLM

**การปรับใช้ผู้ใช้ Root** ตามค่าเริ่มต้นในอิมเมจ Docker อย่างเป็นทางการของ LiteLLM โดยไม่มีการแยกสิทธิ์หรือกลไก sandboxing

### การแยกที่บังคับของ OpenLegion

**การรันแบบชั่วคราว** แต่ละงานรันตามต้องการในแซนด์บ็อกซ์ที่ไม่มีการเข้าถึงเครือข่ายเป็นค่าเริ่มต้นแล้วหยุด จึงไม่มีโพรเซส agent ที่อยู่ยาวให้ยกระดับสิทธิ์

## มุมมองของ OpenLegion

CVE-2026-42208 (CVSS 9.8 CRITICAL ซึ่ง CISA ยืนยันว่าถูกโจมตีจริง) พิสูจน์ว่า SQL injection สามารถเปิดเผยที่เก็บข้อมูลรับรองขององค์กรทั้งหมดได้ vault ข้อมูลรับรองของ OpenLegion ขจัดความเสี่ยงในการรวมข้อมูลรับรองได้อย่างสมบูรณ์

## เลือก LiteLLM เทียบกับ OpenLegion

### เลือก LiteLLM เมื่อการรวม gateway เป็นสิ่งสำคัญ

ทีมของคุณต้องการการผสานรวมผู้ให้บริการที่เรียบง่ายพร้อมการเข้าถึง API แบบรวมสำหรับ LLM provider กว่า 100 ราย

### เลือก OpenLegion เมื่อความปลอดภัยของข้อมูลรับรองเป็นสิ่งสำคัญ

การรวมข้อมูลรับรองสร้างความเสี่ยงที่ยอมรับไม่ได้ซึ่งการเจาะระบบส่วนประกอบหนึ่งอาจเปิดเผย API key ขององค์กรทั้งหมด

สำหรับมุมมองที่กว้างขึ้นเกี่ยวกับ [สถาปัตยกรรมความปลอดภัยของ AI agent](/learn/ai-agent-security) รูปแบบการแยกข้อมูลรับรองคือตัวสร้างความแตกต่างด้านความปลอดภัยที่สำคัญที่สุดของ OpenLegion

## คำถามที่พบบ่อย

### LiteLLM เทียบกับ OpenLegion คืออะไร?

LiteLLM คือ LLM gateway แบบรวมศูนย์ที่มีมากกว่า 62,615 GitHub stars ซึ่งรวมข้อมูลรับรองสำหรับการเข้าถึงแบบรวมให้กับ LLM provider กว่า 100 ราย OpenLegion คือแพลตฟอร์ม multi-agent ที่ให้ความสำคัญกับความปลอดภัย ซึ่งข้อมูลรับรองอยู่ใน vault และถูกฉีดเข้าไปนอกโมเดล

### ช่องโหว่ความปลอดภัยล่าสุดของ LiteLLM มีอะไรบ้าง?

CVE-2026-42208 (CVSS 9.8 CRITICAL) อนุญาตให้ SQL injection ที่ไม่ต้องผ่านการรับรองความถูกต้องอ่าน และอาจแก้ไข ฐานข้อมูลข้อมูลรับรองทั้งหมดผ่าน Authorization header ที่สร้างขึ้น กระทบเวอร์ชัน 1.81.16 ถึง 1.83.6 แพตช์ใน v1.83.7 และอยู่ในแคตตาล็อก Known Exploited Vulnerabilities ของ CISA CVE ร้ายแรงอื่นในปี 2026 ได้แก่ การไม่ตรวจสิทธิ์ผู้ดูแลระบบบน /config/update ที่นำไปสู่ RCE (CVE-2026-35029), คีย์แคช OIDC ชนกันจนสวมรอยเป็นผู้ใช้อื่นได้เมื่อเปิดใช้ JWT (CVE-2026-35030), การหนีออกจาก sandbox ใน custom-code guardrail (CVE-2026-40217) และ SSTI RCE ที่ /prompts/test (CVE-2026-42203) NVD ระบุ CVE ของ LiteLLM ที่เผยแพร่ในปี 2026 มากกว่า 30 รายการ

### พวกเขาจัดการข้อมูลรับรองผู้ให้บริการ LLM อย่างไร?

LiteLLM จัดเก็บข้อมูลรับรองของผู้ให้บริการทั้งหมดในฐานข้อมูลแบบรวมศูนย์ vault ของ OpenLegion ฉีดข้อมูลรับรองในเวลาที่เรียกใช้ นอกโมเดล ซึ่งถือเพียง handle เท่านั้น

### อันไหนปลอดภัยกว่าสำหรับ production?

LiteLLM รวมข้อมูลรับรองทั้งหมดสร้างเป้าหมายการโจมตีมูลค่าสูงที่พิสูจน์แล้วว่าเสี่ยงต่อ SQL injection แบบ CRITICAL OpenLegion เก็บข้อมูลรับรองใน vault ที่โมเดลไม่เคยอ่าน ให้ทุกงานมีการรันในแซนด์บ็อกซ์ของตัวเอง และไม่มีโพรเซส agent ที่อยู่ยาวให้บุกรุก

### ความแตกต่างในการปรับใช้คืออะไร?

LiteLLM ทำงานในฐานะ root ในอิมเมจ Docker ตามค่าเริ่มต้นโดยไม่มี sandboxing OpenLegion เป็นเว็บแอปที่โฮสต์ให้โดยไม่มีอะไรต้องดีพลอย: เข้าสู่ระบบด้วย Google และแต่ละงานรันตามต้องการในแซนด์บ็อกซ์ที่ไม่มีการเข้าถึงเครือข่ายเป็นค่าเริ่มต้น

### ฉันสามารถย้ายจาก LiteLLM ไปยัง OpenLegion ได้หรือไม่?

ได้ ไม่มีการกำหนดค่าผู้ให้บริการให้โอนถ่าย เพราะ OpenLegion เลือกโมเดลด้วยพรีเซ็ต — Smartest, Smart หรือ Normal ข้อมูลรับรองที่ agent ยังต้องใช้ย้ายเข้าสู่ vault ซึ่งโมเดลถือเพียง handle
