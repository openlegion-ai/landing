# بديل LiteLLM: OpenLegion Vault الموزع مقابل البوابة المركزية

يمثل OpenLegion مقابل LiteLLM المقايضة الأمنية الجوهرية بين بيانات اعتماد محفوظة في خزنة تُحقن خارج النموذج وتجميع بيانات الاعتماد عبر بوابة LLM مركزية. يتفوق LiteLLM كبوابة موحدة للمزودين بـ 62,615 نجمة على GitHub وتتبع التكاليف ودعم أكثر من 100 مزود LLM، لكنه عانى من CVE-2026-42208 (CVSS 9.8 CRITICAL، مدرجة في كتالوج CISA للثغرات المستغلة المعروفة) حيث كشف حقن SQL قاعدة بيانات بيانات الاعتماد بأكملها للمهاجمين غير المصادق عليهم. في OpenLegion تعيش بيانات الاعتماد في خزنة وتُحقن في وقت الاستدعاء، ولا يحمل النموذج سوى مُعرِّف مرجعي — فلا توجد قاعدة بيانات بيانات اعتماد لقراءتها.

<!-- SCHEMA: DefinitionBlock -->

> **ما هو LiteLLM وكيف يُقارن بـ OpenLegion؟**
> LiteLLM هو بوابة LLM مركزية بأكثر من 62,615 نجمة على GitHub تجمع بيانات اعتماد المزود في قاعدة بيانات واحدة للوصول الموحد وتتبع التكاليف وتوجيه المزودين. OpenLegion هو منصة متعددة الوكلاء تعطي الأولوية للأمان حيث تعيش بيانات الاعتماد في خزنة وتُحقن خارج النموذج، مما يلغي قواعد بيانات بيانات الاعتماد كأهداف هجوم.

## البوابة المركزية مقابل Vault الموزع

### تجميع بيانات الاعتماد مقابل حقن Vault

يركز **LiteLLM** جميع بيانات اعتماد مزود LLM في قاعدة بيانات واحدة يمكن الوصول إليها عبر نقاط API. أثبت CVE-2026-42208 هذا الخطر عندما كشف حقن SQL قاعدة بيانات بيانات اعتماد LiteLLM بأكملها للمهاجمين غير المصادق عليهم.

يحفظ **OpenLegion** الوصول إلى بيانات الاعتماد في خزنة لا تُنسخ أبدًا إلى أي موقع يمكن للوكلاء الوصول إليه. تُحقن بيانات الاعتماد خارج النموذج، ولا يحمل النموذج سوى مُعرِّف مرجعي.

## مجموعة CVE 2026: عندما تصبح المركزية عبئًا

### CVE-2026-42208: حقن SQL CRITICAL

**CVSS 9.8 CRITICAL** ثغرة خطورة (درجة CVSS 3.1 لدى NVD؛ ودرجة CVSS 4.0 لدى GitHub هي 9.3) حيث كشف حقن SQL في التحقق من مفتاح API لـ LiteLLM قاعدة بيانات بيانات الاعتماد بأكملها للمهاجمين غير المصادق عليهم. أثّرت على الإصدارات من 1.81.16 حتى 1.83.6 وصُحّحت في الإصدار 1.83.7، وأضافتها CISA إلى كتالوج الثغرات المستغلة المعروفة (KEV) في 8 مايو 2026، ما يؤكد استغلالها فعليًا.

### نمط CVE 2026: خمس ثغرات في أربعة أشهر

نُشرت **خمسة CVEs خطيرة** بين أبريل ومايو 2026، وهي جزء فقط من إجمالي العام: تُدرج NVD أكثر من 30 CVE لـ LiteLLM نُشرت في 2026:

1. **CVE-2026-42208** (CVSS 9.8 CRITICAL) - حقن SQL يكشف قاعدة بيانات بيانات الاعتماد للمهاجمين غير المصادق عليهم. صُحّحت في 1.83.7.
2. **CVE-2026-35029** (CVSS 8.8 HIGH) - غياب التحقق من صلاحية المسؤول على `/config/update`: يمكن لأي مستخدم مصادق عليه تعديل تكوين البروكسي وتسجيل معالجات pass-through تشير إلى كود Python يتحكم فيه المهاجم، ما يحقق RCE. صُحّحت في 1.83.0.
3. **CVE-2026-35030** (CVSS 9.1 CRITICAL) - تصادم مفتاح ذاكرة التخزين المؤقت لـ OIDC userinfo: عند تفعيل مصادقة JWT (غير مفعّلة افتراضيًا)، يرث رمز مصنوع تطابق أحرفه العشرون الأولى رمزًا مخزّنًا مؤقتًا لمستخدم شرعي هويةَ ذلك المستخدم. صُحّحت في 1.83.0.
4. **CVE-2026-40217** (CVSS 8.8 HIGH) - تنفيذ كود عبر إعادة كتابة bytecode على `/guardrails/test_custom_code`، وهو هروب sandbox في حاجز الكود المخصص. صُحّحت في 1.83.10.
5. **CVE-2026-42203** (CVSS 8.8 HIGH) - حقن قالب جانب الخادم (SSTI) RCE على `/prompts/test`: كانت قوالب الموجّهات تُعرض دون sandbox، فيمكن لأي حامل مفتاح API صالح للبروكسي تشغيل كود داخل عملية البروكسي. أثّرت على الإصدارات من 1.80.5 حتى 1.83.6؛ صُحّحت في 1.83.7.

## أمان الحاويات: تنفيذ Root مقابل المعزول

### تنفيذ Root الافتراضي لـ LiteLLM

**نشر مستخدم Root** بشكل افتراضي في صورة Docker الرسمية لـ LiteLLM دون فصل الامتيازات أو آليات sandboxing.

### العزل الإلزامي لـ OpenLegion

**التنفيذ سريع الزوال** يحلّ محل العامل طويل الأمد: تعمل كل مهمة عند الطلب ثم تتوقف، فلا توجد عملية وكيل قائمة يمكن التصعيد منها.

## رأي OpenLegion

أثبت CVE-2026-42208 (CVSS 9.8 CRITICAL، مستغلة فعليًا وفق CISA) أن حقن SQL يمكنه كشف مخازن بيانات الاعتماد التنظيمية بأكملها. تلغي خزنة بيانات الاعتماد في OpenLegion مخاطر تجميع بيانات الاعتماد تمامًا.

## اختيار LiteLLM مقابل OpenLegion

### اختر LiteLLM عندما تكون توحيد البوابة هي الأولوية

يحتاج فريقك إلى تكامل مبسط للمزودين مع وصول API موحد لأكثر من 100 مزود LLM.

### اختر OpenLegion عندما يكون أمان بيانات الاعتماد ضروريًا

يخلق تجميع بيانات الاعتماد مخاطر غير مقبولة حيث قد يؤدي اختراق مكون واحد إلى كشف جميع مفاتيح API التنظيمية.

## الأسئلة المتكررة

### ما هو LiteLLM مقابل OpenLegion؟

LiteLLM هو بوابة LLM مركزية بأكثر من 62,615 نجمة على GitHub تجمع بيانات الاعتماد في قاعدة بيانات للوصول الموحد لأكثر من 100 مزود LLM. OpenLegion هو منصة متعددة الوكلاء تعطي الأولوية للأمان حيث تعيش بيانات الاعتماد في خزنة وتُحقن خارج النموذج دون تخزين مركزي.

### ما هي ثغرات الأمان الأخيرة في LiteLLM؟

CVE-2026-42208 (CVSS 9.8 CRITICAL) سمح بحقن SQL دون مصادقة لقراءة قاعدة بيانات بيانات الاعتماد بأكملها، وربما تعديلها، عبر رؤوس Authorization المصنوعة؛ أثّر على الإصدارات من 1.81.16 حتى 1.83.6، وصُحّح في 1.83.7، وهو مدرج في كتالوج CISA للثغرات المستغلة المعروفة. تشمل CVEs خطيرة أخرى في 2026 غياب التحقق من صلاحية المسؤول على /config/update مما يتيح RCE (CVE-2026-35029)، وتصادم مفتاح ذاكرة OIDC المؤقتة الذي يتيح انتحال هوية مستخدم آخر عند تفعيل مصادقة JWT (CVE-2026-35030)، وهروب sandbox في حاجز الكود المخصص (CVE-2026-40217)، وSSTI RCE على /prompts/test (CVE-2026-42203). تُدرج NVD أكثر من 30 CVE لـ LiteLLM نُشرت في 2026.

### كيف يتعاملان مع بيانات اعتماد مزود LLM؟

يخزن LiteLLM جميع بيانات اعتماد المزود في قاعدة بيانات مركزية يمكن الوصول إليها عبر نقاط API. تحقن خزنة OpenLegion بيانات الاعتماد في وقت الاستدعاء خارج النموذج، دون تخزينها في أي موقع يمكن للوكلاء الوصول إليه.

### أيهما أكثر أمانًا للإنتاج؟

يجمع LiteLLM جميع بيانات الاعتماد مما يخلق هدف هجوم عالي القيمة ثبت أنه عرضة لحقن SQL CRITICAL. يحفظ OpenLegion بيانات الاعتماد في خزنة لا يقرأها النموذج، ويمنح كل مهمة تشغيلاً خاصاً في صندوق رمل، ولا يترك عملية وكيل طويلة الأمد لاختراقها.

### ما هي الاختلافات في النشر؟

يعمل LiteLLM كـ root في صورة Docker الافتراضية دون sandboxing. OpenLegion تطبيق ويب مُستضاف لا شيء فيه لنشره: سجّل الدخول عبر Google، وتعمل كل مهمة عند الطلب في صندوق رمل دون وصول إلى الشبكة افتراضياً.

### هل يمكنني الانتقال من LiteLLM إلى OpenLegion؟

نعم، ولا توجد تكوينات مزود تُنقل لأن OpenLegion يختار النماذج عبر إعدادات مسبقة: الأذكى أو ذكي أو عادي. تنتقل بيانات الاعتماد التي تحتاجها أدواتك إلى الخزنة، حيث لا يحمل النموذج سوى مُعرِّف مرجعي.
